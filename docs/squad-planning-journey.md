# From Repository Analysis to an Assigned Coding Task with Squad

The journey began without a human-authored backlog item. In [Squad Bootstrap run 34909790188](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34909790188), Squad analyzed the `octodemo/eshop-bradyg-dev` repository and generated two review surfaces: [issue #4](https://github.com/octodemo/eshop-bradyg-dev/issues/4), containing repository-derived research proposals, and [Cast PR #3](https://github.com/octodemo/eshop-bradyg-dev/pull/3), containing a proposed team roster, charters, and routing configuration. The pull request was created as a normal pull request, not a GitHub draft, even though its content explicitly described the Cast as a proposal requiring human review.

![Swimlane diagram of the Squad planning journey from repository analysis through human steering and task assignment to draft PR creation](diagrams/squad-planning-journey.svg)

*Squad generated evidence, structure, and durable work artifacts. The human narrowed the opportunity, selected and revised the technical strategy, approved the plan, and authorized the first coding task.*

That distinction mattered. Issue #4 opened with a clear boundary: the opportunities were “proposals, not approved work,” and nothing had been implemented, merged, or authorized. Of five suggested areas, P1 focused on expanding test coverage for the .NET Aspire resource graph in `src/eShop.AppHost/Program.cs`. The hypothesis was practical: missing resources, references, connection strings, or startup-order dependencies should be caught during builds rather than discovered when the distributed application runs.

The first consequential human action was to narrow the machine-generated opportunity set. Brady issued:

> `/squad research Focus only on proposal P1: assess current AppHost unit test coverage gaps against the resource graph in src/eShop.AppHost/Program.cs and recommend specific test additions.`

[Research run 34912077979](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34912077979) compared the current AppHost tests with the actual resource graph. It found that existing tests primarily covered helper methods, while the full graph, important `WaitFor` edges, mobile-BFF routes, and endpoint-scheme selection lacked direct coverage. It also surfaced a key decision, R7: either refactor the graph into a testable unit or use `Aspire.Hosting.Testing` and `DistributedApplicationTestingBuilder` against `Program.cs` as written.

The research was specific enough to become planning input rather than a generic testing recommendation. It identified missing assertions for Redis, RabbitMQ, PostgreSQL databases, and project resources; called out startup ordering between `order-processor`, `ordering-api`, and `orderingdb`; and separated full-model testing from extension-level tests for YARP configuration. Just as importantly, it stated non-goals: no containers, no running AppHost integration environment, and no unrelated service tests. That boundary kept a broad repository-analysis result from turning into an open-ended modernization project. The agent supplied the inventory and tradeoffs, while the next commands determined which findings could become authorized work.

From there, Squad handled the mechanical transformation from findings to structured work. `/squad triage` in [run 34912792934](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34912792934) separated actionable gaps, supporting evidence, and the unresolved testing-strategy decision. `/squad plan program` in [run 34915757617](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34915757617) organized the work into an initiative, four epics, two milestones, and dependencies. Then Brady selected the technical direction while requesting the implementation breakdown:

> `/squad plan implementation`
>
> `Resolve R7 with Option A: use Aspire.Hosting.Testing's DistributedApplicationTestingBuilder to test Program.cs as-is, without refactoring the resource graph.`

[Run 34916584544](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34916584544) applied Option A, but its first plan represented the decision as a standalone documentation task and made all later work depend on it. The result was structurally tidy, yet it did not allocate technical risk where the risk actually lived.

The central steering moment came several hours later. With `/squad plan program revise`, Brady instructed Squad to preserve Option A only conditionally; replace the standalone decision record with a compile-level implementation spike; stop and return the plan for revision if the spike failed; and leave the unrelated mobile-BFF and endpoint-scheme tests unblocked. [Revision run 34937726709](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34937726709) produced a new authoritative program plan with exactly that shape. This was not a cosmetic edit. A human changed the risk model, failure behavior, and dependency graph while retaining the agents' useful research.

Squad then regenerated the task breakdown in [implementation run 34938759188](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34938759188). The plan now started with a compile-level spike that had to build and inspect the application model without starting containers. Resource-existence and `WaitFor` tests depended on that proof; mobile-BFF route coverage and `ShouldUseHttpForEndpoints` tests remained independent.

![Tree diagram of the activated AppHost test tasks, showing the compile-level spike gating two model tests while two extension-level tests remain independent](diagrams/squad-task-topology.svg)

*The revised topology placed uncertainty where it belonged: issue #22 became a technical gate for issues #23 and #24, with an explicit stop-and-revise path. Issues #25 and #26 remained independent.*

[Validation run 34949834507](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34949834507) passed the plan, but did not simply rubber-stamp it. It reported four meaningful, non-blocking warnings: timebox the spike and make the fallback explicit; avoid tautological `WaitFor` assertions by using an independently authored expectation or mutation; verify that relocating endpoint-scheme logic changes no behavior; and track the roughly 13 mobile-BFF routes left outside the initial two-route sample. The validator also called out the single Test-agent bottleneck and the deliberate absence of runtime end-to-end coverage as accepted risks.

Approval remained deliberately separate from generation. Brady accepted scope with `/squad plan accept scope` in [run 34985582578](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34985582578), accepted the implementation plan with `/squad plan accept implementation` in [run 34986842391](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34986842391), and finally activated it with `/squad plan activate` in [run 34987615314](https://github.com/octodemo/eshop-bradyg-dev/actions/runs/34987615314). These were distinct gates: scope lock, task lock, and backlog creation.

Activation created [four epic issues](https://github.com/octodemo/eshop-bradyg-dev/issues/18) and five implementation tasks, [#22](https://github.com/octodemo/eshop-bradyg-dev/issues/22) through [#26](https://github.com/octodemo/eshop-bradyg-dev/issues/26). The planned milestones were not created as GitHub milestone objects because the run's safe-output tools did not support milestone creation; instead, milestone assignments were preserved in the generated issue bodies.

There is also an operational nuance worth retaining. The revision, implementation-acceptance, and activation runs received overall failure conclusions because ancillary lifecycle-state upserts rejected their generated lifecycle summaries. The durable outputs still existed: the revised plan comment, accepted implementation artifact, epics, tasks, labels, and activation bindings were created successfully. A red workflow conclusion, in this case, did not mean the planning transaction had produced no usable result.

The handoff to coding was human-controlled too. On September 15, Brady assigned [issue #22](https://github.com/octodemo/eshop-bradyg-dev/issues/22), the compile-level risk spike, to the GitHub Copilot coding agent at **15:46:17 UTC**. Eight seconds later, at **15:46:25 UTC**, Copilot opened [draft PR #28](https://github.com/octodemo/eshop-bradyg-dev/pull/28). Agents performed the repository analysis, evidence gathering, planning mechanics, validation, hierarchy creation, and coordination. The human made the consequential choices: what to investigate, which technical option to pursue, how failure should behave, what could proceed independently, when the plan was acceptable, and which task was authorized for implementation.
